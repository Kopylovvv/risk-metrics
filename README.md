## Локальный запуск backend и PostgreSQL

Требования: установленный и запущенный Docker с Docker Compose.

Все команды выполняются из корня репозитория.

### Первый запуск

Скопировать шаблон настроек:

```bash
cp .env.example .env
```

Заполнить в `.env` имя базы, пользователя и локальный пароль.
Файл `.env` исключён из Git.

Проверить конфигурацию, собрать backend и запустить окружение:

```bash
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
```

Compose выполняет три шага:

1. `db` — PostgreSQL 18.6; дождаться успешного healthcheck.
2. `migrate` — из образа backend выполнить `alembic upgrade head` и завершиться с кодом 0.
3. `backend` — запустить FastAPI; дождаться `/health/ready` с проверкой подключения к БД.

В `docker compose ps --all` сервисы `db` и `backend` должны быть `healthy`,
а `migrate` — `Exited (0)`. Завершение `migrate` нормально: это разовая операция.
Ошибка миграции блокирует запуск API; причину можно увидеть через
`docker compose logs migrate`.

- Swagger и примеры запросов: http://localhost:8000/docs
- Процесс API жив: http://localhost:8000/health/live
- API подключается к БД: http://localhost:8000/health/ready
- Контракт, модель БД и ручной запуск Python: [backend/README.md](backend/README.md).

Python и его зависимости установлены внутри образа, отдельно на компьютер их ставить
для этого запуска не нужно. `--build` пересобирает образ после изменений исходников.
Новый `up` повторно применяет миграции; уже применённые Alembic не выполняет заново.

Frontend пока отсутствует в репозитории. Его контейнер и подключение к API будут
добавлены после появления приложения; текущая команда поднимает backend и БД.
Источники Cbonds/RuData пока заменены заглушками, поэтому запуск окружения
не подтверждает получение реальных рыночных данных.

### Настройки и адреса

| Настройка | По умолчанию | Что означает |
|---|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | из `.env` | база, пользователь и локальный пароль |
| `POSTGRES_PUBLISHED_PORT` | `5433` | порт БД на компьютере разработчика |
| `BACKEND_PORT` | `8000` | порт API на компьютере разработчика |
| `ALLOWED_ORIGINS` | localhost/127.0.0.1 на 5173 и 8000 | допустимые адреса браузерного интерфейса |
| `COOKIE_SECURE` | `false` | локальный HTTP; при развёртывании с HTTPS нужен `true` |

Внутри сети Compose backend и миграции обращаются к **`db:5432`**.
`localhost:5433` — адрес для программы на твоём компьютере, а не внутри backend-контейнера.
Порты опубликованы только на `127.0.0.1`, поэтому этот запуск предназначен для локальной
разработки. Если порт занят, измени соответствующее значение в `.env`;
при смене адреса браузерного интерфейса обнови `ALLOWED_ORIGINS`.

Файл `.env` Compose использует для подстановки значений, а секция `environment`
передаёт нужные переменные в контейнеры. Сам файл в образ не копируется.
Изменение `POSTGRES_*` не меняет имя базы или пароль в уже созданном volume:
эти переменные инициализируют только пустую базу.

### Контрольные данные для локальной демонстрации

Необязательная команда добавляет демонстрационные облигации и курс валют в локальную БД:

```bash
docker compose exec backend python -m app.stubs.demo_data
```

Это контрольные данные из кода, а не ответы реального источника.

### Подключение

С компьютера база доступна по адресу `localhost:5433`.

Для подключения через клиент внутри контейнера:

```bash
docker compose exec db psql -h 127.0.0.1 -U risk_metrics -d risk_metrics -W
```

Команда предполагает, что имя пользователя и базы в `.env` — `risk_metrics`.
Пароль берётся из `.env` и вводится по запросу.

Для выхода из клиента: `\q`.

### Логи и остановка

Посмотреть последние сообщения:

```bash
docker compose logs --tail=50 backend migrate db
```

Остановить и удалить контейнер, сохранив данные:

```bash
docker compose down
```

Данные PostgreSQL хранятся в именованном volume.
Команда `docker compose down -v` удаляет этот volume вместе с данными.

Обычные `down` и повторный `up --build -d --wait` пересоздают контейнеры, сохраняя
базу, сделки и сессии. Для работы только с базой (например, при запуске Python
вне контейнера) используй `docker compose up -d --wait db`.

### Независимая проверка запуска

Из корня репозитория, при работающем Docker и установленном Python 3:

```bash
python3 scripts/check_compose.py
```

На Windows команда обычно называется `python`. Проверке нужны Docker Compose
с поддержкой `up --wait` и свободные порты `18000` и `15433`; при необходимости:

```bash
python3 scripts/check_compose.py --backend-port 18001 --db-port 15434
```

Проверка создаёт уникальный временный Compose-проект, свои учётные данные и volume.
Она проверяет миграции, HTTP API, запись сделки и сохранение данных/сессии после
пересоздания контейнеров, ошибку readiness без БД и запрет запуска API при ошибке
миграции. В конце удаляются только контейнеры и volume этого временного проекта;
обычный `risk-metrics` и его данные не используются.

Другому участнику нужно повторить обычный запуск по инструкции и записать результат
в #17: версия/коммит, ОС, статусы контейнеров, доступность `/docs` и `/health/ready`.
Автоматическая проверка не заменяет это подтверждение участника.

## Общие правила Git

`.gitignore` исключает локальные `.env`, зависимости, сборки, кэши, отчёты
проверок и настройки JetBrains / VS Code. Шаблоны `.env.example` и
`.env.*.example` остаются доступными для добавления в Git.

Исходники, миграции, Dockerfile, Compose, настройки инструментов проекта
и lock-файлы зависимостей необходимо хранить в репозитории.

## CI

Workflow `.github/workflows/ci.yml` запускается при push в ветку и при
создании или обновлении Pull Request. Он проверяет изменённые строки и
Compose, поднимает PostgreSQL 18.6, записывает контрольную строку и проверяет
её сохранность после пересоздания контейнера.

База CI создаётся на отдельной машине GitHub с тестовыми настройками.
В конце проверки контейнер и его volume удаляются. Локальная база
разработчика не используется. Доступ к Cbonds / RuData и тестовый сервер
для этой проверки не требуются.

Workflow `.github/workflows/backend.yml` уже проверяет Ruff, миграции и тесты на
настоящем PostgreSQL, а затем собирает образ backend. Workflow
`.github/workflows/compose.yml` запускает описанную выше проверку общего окружения
на пустой временной базе. Доступ к платному API для этих проверок не нужен.

Проверки и сборка frontend будут подключены после появления приложения.
Задача #18 остаётся открытой до проверки всего заявленного объёма.
Workflow зеркалирования GitLab выполняет отдельную задачу.
