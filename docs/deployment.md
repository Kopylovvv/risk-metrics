# Полный запуск и тестовый стенд

## Как проходит запрос

Браузер → порт frontend (по умолчанию 8080) → Nginx → backend:8000 → db:5432.
HTML, CSS и JavaScript Nginx отдаёт из `/usr/share/nginx/html`. Запрос `/api/v1/...`
передаётся в backend с исходным путём, cookie, Origin и заголовком X-CSRF-Token.
Браузер обращается к одному адресу; адреса сервисов Docker ему знать не нужно.

Dockerfile frontend содержит две стадии. В `build` Node.js устанавливает зависимости
по package-lock.json и выполняет `npm run build`. В `runtime` Nginx получает только
готовый `dist` и конфигурацию; Node.js и исходники в рабочую стадию не копируются.
Nginx работает от пользователя nginx на порту 8080, временные файлы хранит в /tmp.

Параметры Vite задаются во время сборки: `/api` и `VITE_USE_MOCKS=false`.
Изменение переменных в уже запущенном контейнере не пересобирает JavaScript.
Локальные `.env` исключены из контекста сборки; пароли БД нужны только backend и db.

## Порядок запуска

`db healthy → migrate Exited (0) → backend healthy → frontend healthy`.
Миграции выполняет отдельный разовый сервис. Alembic хранит версию схемы и пропускает
уже применённые миграции. Ошибка миграции блокирует запуск backend и frontend.

Frontend проверяет свой `/healthz`; готовность API и БД проверяется отдельно через
`/health/ready` (доступен и на порту frontend). При недоступной БД страница может
оставаться доступной, а API возвращает 503. Nginx обновляет DNS-адрес backend через
встроенный DNS Docker: пересоздание API не требует пересборки страницы.

## Первый запуск

В корне репозитория при работающем Docker:

```bash
cp .env.example .env
```

Задать локальные POSTGRES_DB, POSTGRES_USER и POSTGRES_PASSWORD. Для существующего
стенда сохранить его `.env`: эти значения не меняют пользователей уже созданной БД.

```bash
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps --all
```

Открыть http://localhost:8080. Swagger доступен на http://localhost:8000/docs.
Порты frontend/API/БД опубликованы на loopback. Порт интерфейса меняется через
FRONTEND_PORT в корневом .env. Compose добавляет localhost и 127.0.0.1 с этим портом
в ALLOWED_ORIGINS, сохраняя остальные настроенные origin. Для другого имени хоста
или публичного HTTPS-адреса добавить точный origin в ALLOWED_ORIGINS.

## Доступ к VM через SSH

При существующем разрешённом SSH-доступе на своём компьютере:

```bash
ssh -N -L 127.0.0.1:8080:127.0.0.1:8080 LOGIN@HOST
```

LOGIN/HOST предоставляет владелец стенда; каждый использует свой разрешённый ключ.
У Александра настроен alias teahorses, который можно использовать вместо LOGIN@HOST.
Оставить терминал работающим и открыть http://127.0.0.1:8080. Эта схема не требует
публиковать порт БД или API в интернет. Если локальный порт занят, освободить его либо
согласовать другой порт и соответствующий ALLOWED_ORIGINS.

## Обновление проверенной версии

Перед обновлением записать `git rev-parse HEAD`, проверить `git status --short` и
состояние сервисов. Для БД с нужными данными сделать резервную копию и проверить
восстановление. Доступы, .env и volume сохраняются на сервере.

```bash
git pull --ff-only origin main
git rev-parse HEAD
docker compose up --build -d --wait
docker compose ps --all
curl --fail http://127.0.0.1:8080/health/ready
```

Обновлять main только после успешных проверок целевого SHA. Сборка сама по себе не
подтверждает работоспособность уже запущенного стенда: проверить страницу, запись и
чтение сделки, сессию и логи. Автоматический деплой относится к #41.

## Диагностика и сохранность

```bash
docker compose logs --tail=60 frontend backend migrate db
docker compose down
docker compose up -d --wait
```

Обычный down сохраняет volume PostgreSQL. `down -v` удаляет данные. Для проверки
пересоздания только API: `docker compose up -d --no-deps --force-recreate --wait backend`.
Если интерфейс виден, но изменения возвращают 403, проверить Origin и X-CSRF-Token.
При 502 проверить backend и DNS/логи Nginx; при 503 readiness — подключение к БД.

## Приёмка другим участником

Записать участника, дату, ОС, SHA, статусы сервисов и способ доступа в #17/#19.
Открыть интерфейс, добавить контрольную сделку, изменить количество, перечитать после
обновления страницы, удалить её. Проверить понятную ошибку при отсутствии данных.
При согласованном пересоздании контейнеров ранее сохранённые сделки должны остаться.
Не размещать в отчёте cookie, CSRF-токен, .env, приватные ключи или реальные сделки.

Автоматическая проверка: `python3 scripts/check_compose.py`. Она использует отдельные
порты и уникальный проект/volume, отключает внешние источники и удаляет свои ресурсы.
Для ручной проверки временного окружения можно добавить `--keep`: после успеха проект
останется работающим; вывести его имя и удалить через Compose после проверки.
Контрольные данные и успешный CI не подтверждают реальный доступ к Cbonds или
финансовую корректность методики. Конфигурация, тестовый сценарий и инструкция
подготовлены с помощью ИИ; результаты реальных запусков фиксируются в PR.
